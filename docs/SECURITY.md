# Security notes

Perfect SMP Images intentionally allows public viewing and public uploads. That is different from allowing unrestricted server behavior.

## Image types

Uploads are restricted to PNG, JPEG and WEBP MIME types. The Worker does not accept arbitrary HTML, SVG, JavaScript or executable files through the image endpoint.

SVG is deliberately excluded because it can contain active content and external references depending on how it is served/embedded.

## Maximum upload size

The default maximum is 15 MB. The frontend validates this before upload and the Worker validates it again. Server-side validation is the security boundary; frontend validation is only a convenience.

## Public raw objects

Raw image responses include `X-Content-Type-Options: nosniff` and use the stored image MIME type. R2 object keys are never accepted directly from a browser request. The public API resolves an image ID to the corresponding object key through D1.

## Delete tokens

Delete tokens are capability credentials. Treat them as secrets.

The token is generated by the Worker, returned to the uploader once and stored by the frontend in localStorage. The database stores only the SHA-256 hash.

Do not add delete tokens to public URLs. Do not put them into Minecraft chat. Do not return `delete_hash` from public API endpoints.

## Admin token

`ADMIN_DELETE_TOKEN` is optional. If configured, create it with `wrangler secret put ADMIN_DELETE_TOKEN`. It must remain a Worker secret and must never be inserted into `wrangler.toml`, GitHub source, frontend code or plugin config.

## Plugin remote downloads

The Minecraft plugin does not accept arbitrary remote image hosts. This is an intentional SSRF defense.

Accepted input can be a plain Perfect SMP image ID or a URL whose host exactly matches `allowed-host` / `website-url`. The plugin then discards the supplied URL and builds its own `/raw/:id` request.

## Public upload abuse

A completely public upload form can be spammed. Before a large public launch, consider adding one or more Cloudflare controls:

- Turnstile verification on POST `/api/images`
- Workers Rate Limiting
- per-session upload quotas
- moderation / report queue
- admin dashboard using Cloudflare Access

These are deployment policy choices and are not required for the base project to work.

## Content policy / moderation

The repository does not attempt to automatically classify uploaded content. If the site is shared beyond a small trusted server community, moderation becomes important. The optional admin delete token exists so the server owner can remove abusive uploads even when the original uploader token is unavailable.

## CSP

The Worker applies a Content Security Policy to static pages. The frontend does not use third-party script CDNs, which makes a strict `script-src 'self'` policy practical.

If you later add analytics, external fonts or another API origin, update the CSP intentionally instead of weakening it globally.

## D1 search

Search text is supplied through prepared statement bindings. Sort order is selected from a hard-coded mapping rather than concatenating arbitrary user-provided SQL.

## Object immutability

An image ID is never reused. Raw image responses can therefore use long immutable cache headers. Replacing an existing R2 object under the same image ID is not part of the API.

## GitHub secrets

The deploy workflow expects:

- `CLOUDFLARE_API_TOKEN`
- `CLOUDFLARE_ACCOUNT_ID`

Use a Cloudflare API token with only the permissions required to deploy this Worker and manage the configured D1/R2 resources. Never commit account API keys to the repository.
